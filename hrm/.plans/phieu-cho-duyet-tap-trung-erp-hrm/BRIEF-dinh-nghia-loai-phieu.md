# Brief: thêm 1 loại phiếu vào Trung tâm phê duyệt — @cuong61n

Dành cho người (hoặc agent) thêm `ApprovalDefinition` cho 1 loại phiếu. Đọc hết trước khi code. **Chính xác hơn nhanh** — user dặn "đọc code thật kỹ, cần chính xác, không cần nhanh".

## Mục tiêu
Màn **Phiếu chờ duyệt** (phân hệ Trung tâm phê duyệt) hiện đúng những phiếu mà người đăng nhập **duyệt được thật** ở màn gốc của từng loại, và tự cập nhật ngay khi dữ liệu đổi. Mỗi loại phiếu = 1 lớp `*Definition` + test đối soát. Phạm vi: **chỉ code đang chạy trên HRM** (bỏ qua việc ERP ghi thẳng DB; bỏ qua loại mà HRM không có bước duyệt / chỉ có nửa luồng — báo lại, đừng xấp xỉ).

## Đọc trước (theo thứ tự)
1. `hrm-api/Modules/ApprovalCenter/Definitions/ApprovalDefinition.php` (hợp đồng) và `Definitions/Timesheet/AttendanceDefinition.php` (bản MẪU đã kiểm chứng đầy đủ — bám sát cấu trúc, comment, cách tính người duyệt).
2. `hrm-api/Modules/ApprovalCenter/Services/ApprovalInboxService.php` (sync/transition/resolve), `ApprovalInboxQuery.php`, `ApprovalInboxRefresher.php` (nghe DB để sync lại khi quyền/quản lý phòng đổi), `ApprovalVerifier.php`.
3. Tests mẫu: `hrm-api/tests/Feature/ApprovalCenter/AttendanceDefinitionTest.php`, `ApprovalChangeWatcherTest.php`, trait `Concerns/VerifiesApprovalDefinition.php`.
4. Báo cáo quyền duyệt từng màn của nhóm bạn: `.plans/phieu-cho-duyet-tap-trung-erp-hrm/quyen-duyet/*.md` (có file:dòng) + `00-ha-tang-quyen.md` (cách tính quản lý phòng, quyền, công ty). **Các báo cáo chỉ là điểm xuất phát — phải tự đọc lại code gốc và đối chiếu**, số dòng có thể lệch.
5. `.plans/phieu-cho-duyet-tap-trung-erp-hrm/database.md` mục 2–6, 10, 13, 14.

## Việc phải làm cho MỖI loại phiếu
1. **Xác định chính xác**: các cấp (status → chữ BE trả + màu), ai duyệt được từng cấp (mã quyền / tên quyền cũ, điều kiện quản lý phòng — dùng ĐÚNG kiểu "quản lý" mà màn gốc dùng, approver_id đích danh, người được phân công, thủ kho…), phạm vi công ty, hạn duyệt, điều kiện "hết khả năng duyệt". Tìm hàm/cờ mà **nút Duyệt và endpoint duyệt** của màn gốc dùng (vd `can_approve`, `canApprove()`, helper trong Service).
2. **Viết `Definitions/<Nhóm>/<Tên>Definition.php`** (`extends ApprovalDefinition`, namespace `Modules\ApprovalCenter\Definitions\<Nhóm>`; PHP **7.4-compatible**: không `?->`, `match`, enum, constructor promotion, named args, `str_contains`…). Cần: `docType` (snake_case, bất biến), `label` (= tên màn trên menu HRM), `sourceSubsystem` (khoá phân hệ trong `hrm-client/components/subsystems.js`, vd `timesheet`, `finance`, `assign`), `sourceTable`, `modelClass`, `pendingQuery`, `describe` (step, status_text/color từ chính accessor BE của phiếu, code, title, requester_id = **employees.id**, company/department/part, submitted_at, level_started_at, **handler_path = route FE THẬT** — kiểm file `hrm-client/pages/...` có tồn tại và màn đó cho người duyệt thao tác; `approvable_until` nếu có hạn), `approvers` (**employees.id × company_id** duyệt được — tính bằng `PermissionLookup::holders()`, `employeeIdsManagingDepartment`… và lọc đúng như code gốc), `outcome`/`lastAction` (người duyệt + nhận xét), `permissionCodes`, **`truth()`** (gọi ĐÚNG code màn gốc cho người đang đăng nhập — mặc định `$model->can_approve`; loại nào không có cờ như vậy thì gọi đúng hàm kiểm quyền của endpoint duyệt), `watchedTables()` (thêm mọi bảng mà danh sách người duyệt phụ thuộc, vd `employee_manage_departments`, bảng kho/thủ kho, `assign_histories`…), `version()` (bắt đầu 1; đổi logic thì tăng), `pendingForEmployeeInfos()` nếu phiếu có cột người đề xuất là employee_infos.id, `excludeOwn()` mặc định false (code gốc không chặn tự duyệt — nếu loại nào CÓ chặn thì bật true + ghi chú).
3. **Gắn trait** `Modules\ApprovalCenter\Traits\SyncsApprovalInbox` vào model nguồn (thêm `use` + hàm `approvalInboxDocType()`), chỉ model của loại bạn phụ trách. Rà mọi chỗ ghi trạng thái bằng query builder (`->update()`, `DB::table()`) trong code chạy thật; chỗ nào không qua Eloquent thì gọi `ApprovalInboxService::scheduleSync($docType, $id)` tường minh (báo lại danh sách chỗ đã chạm).
4. **`seedTest(int $count)`**: tạo phiếu THỬ đang chờ ở nhiều cấp / nhiều người xin, bằng Eloquent/Service như code thật (để trait tự sync), có người duyệt thật trong DB local, mỗi phiếu gắn chữ `TEST-APPROVAL-CENTER` (trường mô tả/ghi chú/lý do) để nhận ra; **`deleteTest`** nếu cần xoá thêm dòng con. Chạy thử: `php artisan approval-center:seed-test <doc_type> --count=6` rồi `approval-center:clean-test` (xoá sạch). Dữ liệu thử phải đủ phong phú để test e2e: có phiếu ở từng cấp, có phiếu của người khác phòng / công ty khác.
5. **Test** `hrm-api/tests/Feature/ApprovalCenter/<Nhóm>/<Tên>DefinitionTest.php` (`use DatabaseTransactions`, trait `VerifiesApprovalDefinition`): vòng đời sync (gửi → qua cấp → duyệt / từ chối / gửi lại), phiếu hết hạn / hết khả năng duyệt, **`assertDefinitionMatchesTruth` với dữ liệu đủ nhánh** (người có/không có quyền, quản lý phòng / không, nhiều công ty, người xin nghỉ việc nếu liên quan…). Chạy bằng `cd hrm-api && vendor/bin/phpunit tests/Feature/ApprovalCenter/<Nhóm>`.
6. **KIỂM THỬ ĐỘT BIẾN (bắt buộc)**: cố ý làm sai Definition ≥ 2–3 kiểu (bỏ điều kiện quản lý, đổi quyền, bỏ lọc công ty…) và chứng minh test FAIL; chỗ nào test không bắt được thì **bổ sung dữ liệu/ca test** cho tới khi bắt được. Khôi phục file sau mỗi lần. (Trên Attendance: test ban đầu chỉ bắt 1/3 đột biến — đừng tin test xanh khi chưa thử phá.)
7. Chạy `php artisan approval-inbox:verify <doc_type>` (cần phiếu thử trong DB: seed trước) → **0 chênh lệch, positives > 0**.
8. Kiểm API thật: mint JWT (xem cách trong `/tmp/mint.php` hoặc tự viết: `auth('api')->claims(['current_company'=>…,'token_version'=>…])->login($user)`), gọi `GET http://127.0.0.1:8000/api/v1/approval-center/inbox?doc_type=<doc_type>` và `/inbox/counts`; xác nhận `handler_path` mở được trên FE (`http://127.0.0.1:3000`).

## Luật cứng
- **Không sửa file dùng chung** của module: `ApprovalDefinition.php`, `Services/*`, `Http/*`, `Console/*`, `Providers/*`, `Migrations/*`, `Registry` (tự khám phá, không cần đăng ký). Cần sửa gì ở đó thì **dừng và báo lại** (nêu lý do + đề xuất diff), đừng tự sửa — các agent khác đang chạy song song cùng lúc.
- Chỉ sửa: file Definition + test + seed của nhóm bạn, và model nguồn (thêm trait) của loại bạn phụ trách. Một loại nằm ngoài nhóm bạn thì không đụng.
- **Viết nguyên file Definition trong MỘT lần** rồi `php -l` ngay (một file lỗi cú pháp sẽ bị Registry bỏ qua + ghi log nhưng làm test của bạn tự "mất" loại đó).
- Không `migrate`, không sửa schema, không chạy lệnh ghi vào DB ngoài phạm vi: DB local `local_hrm_erp` được ghi dữ liệu thử nhưng **mọi thứ bạn đổi phải khôi phục/dọn** (đột biến: khôi phục file; seed: clean-test; thay đổi vai trò/quản lý phòng để thử: trả lại nguyên trạng, tốt nhất trong `DatabaseTransactions`).
- Nhiều agent chạy PHPUnit **cùng lúc trên cùng DB**: gặp `Deadlock` / `Lock wait timeout` là va chạm tạm — chạy lại; giữ giao dịch ngắn; chỉ chạy test của nhóm bạn (`--filter`/thư mục), đừng chạy cả bộ.
- **Không chạy Playwright / không mở trình duyệt** (người điều phối chạy e2e tuần tự sau). Có thể viết sẵn spec ở `e2e/tests/approval-center/types/<doc_type>.spec.ts` nếu muốn (theo mẫu `e2e/tests/approval-center/inbox.spec.ts` nếu đã có) nhưng đừng chạy.
- Không commit, không push, không deploy. Không sửa CLAUDE.md / skills / docs chung.
- Phát hiện **lỗi / lỗ hổng của code gốc** (BE không kiểm quyền, nhảy cấp, danh sách lệch người duyệt…): chỉ GHI LẠI trong báo cáo, không sửa code nghiệp vụ.
- Không tự phát minh quy tắc: điều gì code không nói thì ghi "chưa xác minh" và đừng đoán. Loại phiếu mà người duyệt không biểu diễn được bằng logic đáng tin → KHÔNG đăng ký (đừng để file Definition trong thư mục), báo lý do.
